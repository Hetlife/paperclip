Backend

The gate is in the API, not the button

A buyer submits the species they want. Screening runs server-side, because a check that only lives in the interface is not a control — anyone can post directly to the endpoint.

Needs review Neon Tetra · Orchid Mantis — No exclusion rule matched. This is not a clearance; legality has not been established.

The screening model is reject-only by design. The verdict type has no approved value and never will — it can say “definitely prohibited”, never “legal”. Legality is per-species and per-jurisdiction, turning on federal law, CITES and destination-state rules. No automated check can settle that.

Readiness checklist required

An inquiry that skips the custodianship checklist is rejected outright by the API — not quietly saved as a lead.

Sanctuary-only is enforced

Requesting an animal marked display-only returns a refusal naming the species. Accepting it would be a promise that can’t be kept.

Consultation, not checkout

There is no cart. The endpoint records an intent to have a conversation — no payment, no reservation, no animal committed.

What is built, and what isn’t

The eventual pipeline — buyer list, researched species, generated 3D model with real behaviour — is several hard problems stacked, not one feature. This is where it actually stands.

Suggested next step: take one specimen — Hydro, the simplest body plan — source real photography by hand, run it through a generation service once, and drop the resulting .glb into the data file. That validates the whole receiving pipeline with zero new code, before deciding what is worth automating.
